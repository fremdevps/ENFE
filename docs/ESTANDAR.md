# Estándar Técnico ENFE — Base de datos, PL/SQL y APEX (V3)

> Reemplaza a `Estandar_Tecnico_Nomenclatura_DB_PLSQL_V2.docx`.
> Objetivo: que **cualquier persona (o Claude) genere siempre el mismo nombre** para el mismo
> objeto, que nada choque al sumar apps nuevas y que todo instale igual en OCI y on-premise.
> Basado en Oracle E-Business Suite Naming Standards y Trivadis PL/SQL & SQL Coding Guidelines.

---

## 0. Reglas generales

| # | Regla |
|---|---|
| G1 | Código en **minúsculas**, identificadores en español, `snake_case`. Palabras completas salvo las abreviaturas registradas. |
| G2 | **Máximo 30 caracteres** por identificador (funciona en cualquier Oracle on-prem). |
| G3 | Todo objeto lleva el **código de app** delante (`adm`, `erp`, `crm`…): es lo que garantiza que dos apps nunca choquen en el mismo esquema. |
| G4 | **Un objeto por archivo**, el archivo se llama igual que el objeto (`erp_fin_factura.sql`, `erp_fin_factura_api.pks/.pkb`). |
| G5 | Scripts **re-ejecutables** (idempotentes): `create or replace`, `merge` para datos, DDL de tablas protegido por el build. |
| G6 | Nada exclusivo de una plataforma sin alternativa (ej. `DBMS_CLOUD`). Mínimo soportado: **Oracle 19c + APEX 26.1**. |

### 0.1 Códigos de app y módulo

| Nivel | Formato | Ejemplos |
|---|---|---|
| App | 3 letras | `adm` Administración Central · `erp` ERP · `crm` CRM |
| Módulo | 3 letras, único dentro de la app | `seg` Seguridad · `gen` General · `aud` Auditoría · `fin` Finanzas · `stk` Inventario · `com` Compras · `ven` Ventas · `prd` Producción |

Los códigos se registran en ADM (`adm_seg_aplicacion`, `adm_seg_modulo`) antes de usarse.

### 0.2 Abreviatura de tabla

Cada tabla tiene una **abreviatura de 3–4 letras, única dentro de su app**, registrada en
`apps/<app>/database/ABREVIATURAS.md` y en el comentario de la tabla. Se usa para nombrar sus
objetos derivados (constraints, índices, triggers, secuencias), que así quedan cortos y únicos.

`adm_seg_usuario` → `usu` · `adm_seg_usuario_rol` → `usro` · `erp_fin_factura` → `fac`

## 1. Tablas y columnas

### 1.1 Tablas
**`<app>_<mod>_<entidad>`** — entidad en **singular**, máximo 26 caracteres.

`adm_seg_usuario` · `erp_fin_factura` · `erp_fin_factura_linea` · `erp_stk_movimiento`

Tablas de relación N:M: las dos entidades en orden de dependencia → `adm_seg_rol_permiso`.

### 1.2 Columnas

| Tipo de columna | Regla | Ejemplo |
|---|---|---|
| Clave primaria | `<entidad>_id`, `number generated by default on null as identity` | `factura_id` |
| Clave foránea | **mismo nombre** que la PK referida | `cliente_id` |
| FK con rol (dos FK a la misma tabla, o significado especial) | `<pk_referida>_<rol>` | `empresa_id_defecto`, `usuario_id_aprobador` |
| Código de negocio | `codigo`, `varchar2`, en mayúsculas (CK) | `codigo` |
| Indicador sí/no | `es_` / `tiene_` / `debe_` + `varchar2(1)` con CK `('S','N')` | `es_superadmin` |
| Estado | `estado varchar2(1)` con CK documentado | `A`ctivo `I`nactivo `B`loqueado |
| Fecha sin hora | `fecha_<evento>` `date` | `fecha_emision` |
| Fecha con hora | `fecha_<evento>` `timestamp` | `fecha_ultimo_login` |
| Importes | `number(18,2)` · cantidades `number(18,4)` | `monto_total` |
| Auditoría (obligatorias) | `creado_por`, `fecha_creacion` (DEFAULT ON NULL), `modificado_por`, `fecha_modificacion` (trigger `_bu`) | — |
| Multi-empresa | `empresa_id` en toda tabla transaccional | — |

> No se usa `BOOLEAN` de SQL (solo existe en 23ai): se usa `S/N` para que corra en 19c.

## 2. Constraints e índices

Todos usan **`<app>_<abrev>`** → únicos en el esquema aunque haya 20 apps.

| Objeto | Formato | Ejemplo |
|---|---|---|
| Primary Key | `pk_<app>_<abrev>` | `pk_erp_fac` |
| Foreign Key | `fk_<app>_<abrev_hija>_<abrev_padre>[_<rol>]` | `fk_erp_fac_cli` · `fk_adm_usu_emp_def` |
| Unique Key | `uk_<app>_<abrev>_<columna(s)>` | `uk_adm_usu_username` |
| Check | `ck_<app>_<abrev>_<regla>` | `ck_erp_fac_monto_pos` · `ck_adm_usu_estado` |
| Índice | `idx_<app>_<abrev>_<columna(s)>` | `idx_erp_fac_fecha_emision` |
| Default | **sin nombre** (Oracle no permite nombrar DEFAULT) | — |

Reglas:
- **Toda FK lleva índice** sobre su(s) columna(s) (`idx_<app>_<abrev>_<columna>`): evita bloqueos al borrar/actualizar el padre.
- Si se necesita borrar en cascada, declararlo explícito (`on delete cascade`) y comentarlo.

## 3. Otros objetos de base de datos

| Objeto | Formato | Ejemplo |
|---|---|---|
| Vista | `<app>_<mod>_<nombre>_v` | `adm_seg_usuario_permiso_v` |
| Vista materializada | `<app>_<mod>_<nombre>_mv` | `erp_ven_resumen_mes_mv` |
| Secuencia (solo si no hay identity) | `seq_<app>_<abrev>[_<uso>]` | `seq_erp_fac_numero` |
| Trigger | `trg_<app>_<abrev>_<momento><evento>` | `trg_erp_fac_biu` |
| Tipo objeto | `<app>_<nombre>_typ` | `erp_linea_typ` |
| Tipo colección | `<app>_<nombre>_tab` | `erp_linea_tab` |
| Job (scheduler) | `job_<app>_<accion>` | `job_erp_cierre_diario` |
| Directorio | `dir_<app>_<uso>` | `dir_erp_import` |
| Contexto (VPD) | `ctx_<app>` | `ctx_erp` |

### 3.1 Sufijos de trigger (sin cambios respecto a V2)

`_bi` `_bu` `_bd` `_ai` `_au` `_ad` `_biu` `_aiu` `_biud` `_aiud` `_io`
(b = before, a = after, io = instead of; i = insert, u = update, d = delete)

Triggers **solo** para: auditoría, valores derivados simples y restricciones que un CK no puede
expresar. **La lógica de negocio va en paquetes, nunca en triggers.**

## 4. Paquetes PL/SQL

### 4.1 Nombre
**`<app>_<mod>_<entidad>_<capa>`**

| Capa | Responsabilidad | La llaman | Puede llamar | COMMIT |
|---|---|---|---|---|
| `ctr` | DML de **una sola tabla**: insertar, actualizar, borrar, bloquear | `reg`, `api` | — | Nunca |
| `reg` | Reglas de negocio: validaciones, cálculos, flujos | `api`, otros `reg` | `ctr`, `reg` | Nunca |
| `api` | **Fachada pública** para APEX, ORDS/REST, jobs y otras apps. Valida permisos, orquesta, traduce errores. | APEX, REST, jobs | `reg`, `ctr` (solo lectura) | Solo en jobs/REST; en APEX lo hace APEX |
| `utl` | Utilitarios sin negocio (fechas, textos, logging) | todos | `utl` | Nunca |

Ejemplos: `erp_fin_factura_ctr` · `erp_fin_factura_reg` · `erp_fin_factura_api` · `adm_seg_seguridad_reg` · `adm_gen_texto_utl`

**Regla de oro:** las pantallas APEX y los servicios REST **solo llaman a paquetes `api`**.
(Excepción: la seguridad central `adm_seg_seguridad_reg`, invocada por autenticación/autorización.)
Así se puede cambiar todo lo de adentro sin romper pantallas.

Todo paquete se declara `authid definer` salvo justificación documentada.

### 4.2 Errores

- `raise_application_error` con rango **por app**:

  | App | Rango |
  |---|---|
  | ADM | −20000 … −20099 |
  | ERP | −20100 … −20299 |
  | CRM | −20300 … −20399 |
  | (siguiente app) | bloques de 100–200 |

- Cada paquete `reg` declara sus códigos como constantes `C_ERR_<NOMBRE>` en la especificación.
- Mensajes en español, para el usuario final, sin detalles técnicos.
- `when others` solo para registrar (log) y **re-lanzar**; nunca para silenciar.

## 5. Código PL/SQL

| Elemento | Prefijo | Ejemplo |
|---|---|---|
| Variable local | `V_` | `V_TOTAL_FACTURA` |
| Constante | `C_` | `C_IGV_PORCENTAJE` |
| Variable global de paquete | `G_` | `G_EMPRESA_ID` |
| Cursor | `CUR_` | `CUR_FACTURAS_PENDIENTES` |
| Record | `R_` | `R_FACTURA` |
| Tipo (record/colección) | `T_` | `T_LISTA_IDS` |
| Excepción | `E_` | `E_SALDO_INSUFICIENTE` |
| Función | `F_` | `F_CALCULAR_IMPUESTO` |
| Procedimiento | `P_` | `P_ANULAR_FACTURA` |
| Parámetro IN | `I_` | `I_FACTURA_ID` |
| Parámetro OUT | `O_` | `O_NRO_DOCUMENTO` |
| Parámetro IN OUT | `IO_` | `IO_ESTADO` |

Reglas:
- Llamadas con **notación nombrada** (`I_FACTURA_ID => V_ID`).
- Tipos anclados: `adm_seg_usuario.username%type`, `%rowtype`.
- Nada de SQL dinámico salvo DDL o necesidad justificada; siempre con binds.
- **Excepción documentada**: funciones que APEX invoca con nombres fijos usan esos nombres
  (`p_username`, `p_password` en la función de autenticación).

## 6. Objetos APEX

| Objeto | Regla | Ejemplo |
|---|---|---|
| ID de app | Fijo, por bloques de 100 | ADM `100` · ERP `200` · CRM `300` |
| Alias de app | código de app | `adm`, `erp` |
| Rango de páginas | 1–9 inicio · 10–99 módulo 1 · 100–199 módulo 2 · … · 9000–9998 utilitarios · 9999 login | — |
| Alias de página | minúsculas con guion | `nuevo-usuario` |
| Item | `P<página>_<COLUMNA>` (estándar APEX) | `P31_USERNAME` |
| Región (Static ID) | minúsculas con guion, la entidad | `empresas` |
| Botón | nombre en MAYÚSCULAS = acción | `CREAR`, `GUARDAR`, `ANULAR` |
| Proceso | verbo + objeto | `crear-usuario` |
| LOV compartida | entidad en plural / dominio | `usuarios`, `estado-ai` |
| Authorization scheme | **el mismo código del permiso en ADM** | `ADM_SEG_ROL_GESTIONAR` |
| Código de permiso | `<APP>_<MOD>_<ENTIDAD>_<ACCION>` | `ERP_FIN_FACTURA_ANULAR` |
| Rol | `<APP>_<NOMBRE>` | `ERP_CONTADOR` · `SUPERADMIN` (global) |

Reglas:
- Formato fuente: **APEXlang** (`.apx`, LF). Validar con `apex validate` antes de importar.
- Toda página lleva authorization scheme salvo login y páginas públicas declaradas.
- Las apps **no crean tablas de seguridad**: usan ADM.

## 7. Estructura de archivos

```
apps/<app>/
  database/
    ABREVIATURAS.md          registro de abreviaturas de tablas
    tables/<tabla>.sql       tabla + constraints + índices + comentarios
    views/<vista>.sql
    triggers/<trigger>.sql
    packages/<paquete>.pks / .pkb
    data/<app>_<mod>_<desc>.sql   datos semilla (merge, idempotente)
  install/
    install.sql              orden de instalación (fuente de los Supporting Objects)
    deinstall.sql
  apexlang/                  app APEX (generada/exportada con SQLcl)
tests/e2e/specs/<app>/       pruebas Playwright
```

Los Supporting Objects se generan con `tools/build-supporting-objects.ps1 -App <app>`; **no se editan a mano**.

## 8. Control de versiones

| Tema | Regla |
|---|---|
| Ramas | `main` (producción, solo merges con tag) · `develop` (integración) · `feature/<tema>` · `fix/<tema>` · `docs/<tema>` |
| Commits | Conventional Commits en español: `feat(erp): …`, `fix(adm): …`, `docs: …`, `test(e2e): …`, `build: …`, `refactor: …` |
| Tamaño | Commits chicos, uno por cambio lógico; que cada commit compile/valide |
| Versiones | SemVer con tag anotado en `main`: `v0.1.0`, `v0.2.0`… (MAJOR cambio incompatible · MINOR funcionalidad · PATCH corrección) |
| Antes de merge a develop | `apex validate` OK + suite E2E OK |
| Nunca en git | wallets, contraseñas, `.env*`, `.secrets/` |

---

## 9. Checklist rápido al crear un objeto

1. ¿Lleva el código de app? ¿Mide ≤ 30?
2. ¿La tabla tiene abreviatura registrada y auditoría?
3. ¿Constraints e índices con `<app>_<abrev>`? ¿Índice en cada FK?
4. ¿Agregado a `install.sql` y `deinstall.sql`?
5. ¿APEX llama solo a `*_api`?
6. ¿Prueba E2E para la pantalla nueva?
